# API reference

The mise-en-place API as of Phase 1, plus Phase 3a's JSON 404s and recipe ETags, Phase 3c's snapshot and recipe ids chosen by the client, and so far in Phase 3b a recipe's sections and steps, tags, equipment and images. The design behind it is in the technical spec, §3 (`planning/specs/technical-spec.md`).

## Conventions

- **Base URL:** `http://localhost:3000` in development (`PORT` changes the port). All endpoints are under `/api`.
- **Bodies** are JSON. Send `Content-Type: application/json`; a body sent as anything else is treated as missing and fails validation. Bodies over 100 kB get a 413. The one exception is an image upload, which is `multipart/form-data` (see [Images](#images)).
- **Ids** are UUID strings, generated by the server. The one exception: a new recipe's id may be chosen by the client (see [`POST /api/recipes`](#post-apirecipes)).
- **Timestamps** are ISO 8601 strings in UTC, such as `"2026-11-02T11:18:50.876Z"`.
- **Unknown fields are rejected.** Every body and list query is checked against a strict schema, so a field the endpoint doesn't accept, including server-owned ones like `createdAt` and `orderIndex`, is a 400. So is `id`, except on a new recipe.
- **Numbers must be JSON numbers.** `"2"` is rejected where `2` is expected.
- **Compression:** a response over 1 kB is gzip-compressed when the request's `Accept-Encoding` allows it, as browsers' always do. Images, already compressed, are sent as they are.
- **No authentication.** Access is controlled by the network: localhost in development, Tailscale from Phase 2.
- **CORS:** browsers may call the API from another origin only if it's listed in `CORS_ORIGINS` (comma-separated). By default no other origin is allowed. Allowed origins can also read the `X-Total-Count` and `ETag` headers.

Phase 1's `instructions` (the method as one block of text) is gone from requests and responses. A migration turned each recipe's text into one section, "Method", with a step for each line (technical spec §7.2).

### Ingredient line

One line of a recipe's ingredient list. In responses each line includes its `ingredient`.

| Field | Type | Notes |
|---|---|---|
| `id` | string (UUID) | |
| `recipeId` | string (UUID) | |
| `ingredientId` | string (UUID) | |
| `orderIndex` | integer | Position in the recipe, from 0. Set by the server from the order of the array you send |
| `quantity` | number or null | Greater than 0. Null means "to taste" or unspecified |
| `quantityMax` | number or null | Upper end of a range ("2–3"). Only set when `quantity` is |

## Lists, search and pagination

`GET /api/recipes`, `GET /api/ingredients`, `GET /api/tags` and `GET /api/equipment` take the same query parameters:

| Parameter | Default | Rules |
|---|---|---|
| `search` | none | Fuzzy match on the name. Trimmed; at most 100 characters; blank means no search |
| `limit` | `50` | Page size: a whole number from 0 to 100 |
| `offset` | `0` | How many items to skip: a whole number, 0 or more |

- **Response:** a JSON array (possibly empty) and an `X-Total-Count` header with the number of items, or of search matches, across all pages. `limit=0` returns an empty array, so it gives you just the total.
- **Order:** plain lists by name, then id. Search results by how well they match, then name, then id. The order is stable, so paging with `offset` never repeats or skips an item.
- **Search** matches names that are similar to the term (PostgreSQL trigram `word_similarity` above 0.3), which tolerates typos ("beff" finds "Beef Chili"), or that contain it, ignoring case. `%`, `_` and `\` match literally.
- **Each parameter once.** A repeated parameter (`?search=a&search=b`) or an unknown one (`?serach=beef`) is a 400.
- **`GET /api/recipes` also takes `tag`** (3b): a tag's id, to list only the recipes with it, together with `search` and paging if you like. An unknown tag has no recipes, so the list is empty.

With the sample data loaded:

```http
GET /api/ingredients?search=pepper&limit=1

HTTP/1.1 200 OK
X-Total-Count: 2

[{ "id": "…", "name": "cayenne pepper", … }]
```

Both peppers match equally well, so they're ordered by name; `offset=1` returns `red pepper`.

## Recipes

### `GET /api/recipes`

Lists recipes as summaries, with their tags but without their lines, method or equipment (see [Recipe](#recipe)). Takes `search`, `tag`, `limit` and `offset` (see [Lists](#lists-search-and-pagination)).

```http
GET /api/recipes?tag=e4b1c7a2-3d5f-4e6a-8b9c-0d1e2f3a4b5c&search=chilli
```

**Responses:** 200 with an array of recipe summaries and `X-Total-Count`; 400 for a bad query.

### `GET /api/recipes/:id`

**Responses:** 200 with the [Recipe](#recipe) and its [`ETag`](#etags-and-if-match); 404 `{ "error": "Recipe not found." }`.

### `POST /api/recipes`

Creates a recipe and its lines in one write.

| Field | Required | Rules |
|---|---|---|
| `name` | yes | String, 1–200 characters after trimming |
| `id` | no | A UUID chosen by the client, stored in lowercase. Absent: the server makes one |
| `description` | no | String or null |
| `servings` | no | Integer, 1 to 1000. Default 1. Not null |
| `prepTime`, `cookTime` | no | Integer, 0 to 99999 (about 69 days), or null |
| `sections` | no | Array of `{ name, steps: [{ text, timerSeconds }] }`, in order (3b). Only with `ingredients`. Default: none |
| `ingredients` | no | Array of lines, in recipe order. Default: none |
| `tagIds` | no | Array of existing tags' ids, in the recipe's order, each once (3b). Default: none |
| `equipment` | no | Array of `{ equipmentId, quantity, optional }`, in order (3b). `quantity` is a whole number from 1 to 99, default 1; `optional` a boolean, default false. Default: none |
| `primaryImageId` | no | The main image: one of this recipe's own images, or null (3b). A new recipe has none yet, so only null. Images are added with [`POST /api/recipes/:id/images`](#post-apirecipesidimages) |

Each line in `ingredients`:

| Field | Required | Rules |
|---|---|---|
| `ingredientId` | yes | UUID of an existing ingredient |
| `quantity` | no | Number greater than 0, or null. Absent means null |
| `quantityMax` | no | Number or null. Only allowed with `quantity`, and at least `quantity` |
| `unit` | no | A unit symbol or alias (see [Units](#units)), converted to the symbol. Null, absent or blank means a count |
| `note` | no | String of up to 200 characters, or null |
| `sectionIndex` | no | The line's section, by its position in this body's `sections`, or null for none. Only with `sections` |

Each section in `sections` has a `name` (1–100 characters after trimming) and `steps`, an array that may be empty. Each step has `text` (1–2,000 characters after trimming) and an optional `timerSeconds` (a whole number from 1 to 86,400, or null).

A body with `sections` must also have `ingredients`. New sections get new ids, so the lines are written again with them; without `ingredients`, they'd lose their sections without a word.

```http
POST /api/recipes
Content-Type: application/json

{
  "name": "Garlic Soup",
  "servings": 2,
  "ingredients": [
    { "ingredientId": "3308532b-ec81-4c05-9def-8cd595f0f035", "quantity": 2, "note": "sliced" },
    { "ingredientId": "60c501d9-706a-40b8-813d-5475a6ee1406", "quantity": 6, "unit": "cloves" },
    { "ingredientId": "31058cf2-6901-4ea4-afe7-c98c21e27752", "quantity": null, "note": "to taste" }
  ]
}
```

The second line is stored with `"unit": "clove"`, and the lines get `orderIndex` 0, 1 and 2.

**Choosing the id.** A device that creates a recipe offline picks its id, and sends the same one each time it retries the upload. If an attempt reached the API but its answer was lost, the retry gets 409 instead of making a second copy, so a 409 for an id you chose means the recipe is already there. The web client sends an id with every new recipe.

**Responses:**
- 201 with the created [Recipe](#recipe) and its [`ETag`](#etags-and-if-match)
- 400 `{ "error": "Validation failed.", "fields": { … } }` for a rule above
- 400 `{ "error": "One or more ingredient IDs are invalid." }` when an `ingredientId` is a valid UUID but no such ingredient exists; likewise `"One or more tag IDs are invalid."` and `"One or more equipment IDs are invalid."`
- 400 `{ "error": "primaryImageId must be one of this recipe's images." }`
- 409 `{ "error": "A recipe with that id already exists." }` when `id` is taken. Nothing changes

### `PATCH /api/recipes/:id`

Changes only the fields in the body; the rules are the same as for POST, but every field is optional, and `id` can't be sent. An empty body changes nothing except `updatedAt`.

`ingredients`, `sections`, `tagIds` and `equipment` work like this:

| In the body | Effect |
|---|---|
| Absent | Left untouched |
| An array | All of them are replaced by the array, in its order |
| `[]` | All of them are removed |

There's no way to change a single line, section or step: send the whole list. Everything in one PATCH is written in one transaction, so a refused or stale request changes nothing.

Send `If-Match` to make sure you're not overwriting a change made elsewhere (see [ETags and `If-Match`](#etags-and-if-match)).

**Responses:** 200 with the updated [Recipe](#recipe) and its new `ETag`; 400 as for POST; 404 `{ "error": "Recipe not found." }`; 412 `{ "error": "The recipe has changed since it was loaded." }`.

### `DELETE /api/recipes/:id`

Deletes the recipe with its lines, method, tags, equipment lines and images, the images' files included. The shared ingredients, tags and equipment are kept. Takes `If-Match`, like PATCH.

**Responses:** 200 `{ "message": "Recipe deleted successfully." }`; 404 `{ "error": "Recipe not found." }`; 412 when `If-Match` is out of date.

### ETags and `If-Match`

A recipe's `ETag` changes whenever the recipe does, including when only its lines change. `GET`, `POST` and `PATCH` return it for a single recipe.

To avoid overwriting an edit made on another device, send the ETag you last saw back in `If-Match` on `PATCH` or `DELETE`:

```http
PATCH /api/recipes/7d0f3a5e-1c2b-4e8a-9f61-2b7c4d9e8a10
If-Match: "1763836800123"
Content-Type: application/json

{ "servings": 4 }
```

| `If-Match` | Effect |
|---|---|
| Not sent | No check: the write always goes ahead |
| The current ETag (or a list containing it) | The write goes ahead |
| `*` | The write goes ahead if the recipe exists |
| Anything else, including a weak ETag (`W/"…"`) | 412, and nothing changes |

A recipe that doesn't exist is still a 404, whatever `If-Match` says. Treat the ETag as opaque: its format may change.

## Ingredients

### `GET /api/ingredients`

Lists ingredients. Takes `search`, `limit` and `offset` (see [Lists](#lists-search-and-pagination)).

**Responses:** 200 with an array of [Ingredient](#ingredient) and `X-Total-Count`; 400 for a bad query.

### `GET /api/ingredients/:id`

**Responses:** 200 with the [Ingredient](#ingredient); 404 `{ "error": "Ingredient not found." }`.

### `POST /api/ingredients`

| Field | Required | Rules |
|---|---|---|
| `name` | yes | String. Trimmed and lowercased, then 1–100 characters |

`{ "name": "  Red Onion " }` is stored as `"red onion"`.

**Responses:**
- 201 with the created [Ingredient](#ingredient)
- 400 for a missing, empty or over-long name, or an unknown field
- 409 `{ "error": "That name already exists." }`, after normalising: `"Onion"` clashes with an existing `"onion"`

### `PATCH /api/ingredients/:id`

Renames an ingredient. Takes the same body as POST; `name` is required.

**Responses:** 200 with the updated [Ingredient](#ingredient); 400 as for POST; 404 `{ "error": "Ingredient not found." }`; 409 `{ "error": "That name already exists." }`.

### `DELETE /api/ingredients/:id`

**Responses:**
- 200 `{ "message": "Ingredient deleted successfully." }`
- 404 `{ "error": "Ingredient not found." }`
- 409 `{ "error": "Cannot delete ingredient that is used in recipes." }`. Remove it from those recipes first.

## Tags

A shared list, like ingredients (3b). Every tag these endpoints return carries its `recipeCount`.

### `GET /api/tags`

Lists tags. Takes `search`, `limit` and `offset` (see [Lists](#lists-search-and-pagination)).

**Responses:** 200 with an array of [Tag](#tag) and `X-Total-Count`; 400 for a bad query.

### `GET /api/tags/:id`

**Responses:** 200 with the [Tag](#tag); 404 `{ "error": "Tag not found." }`.

### `POST /api/tags`

| Field | Required | Rules |
|---|---|---|
| `name` | yes | String. Trimmed and lowercased, then 1–50 characters |
| `color` | no | `#rrggbb` (any case, stored lowercase), or null. Default null |

**Responses:** 201 with the [Tag](#tag); 400 for a rule above or an unknown field; 409 `{ "error": "That name already exists." }`, after normalising.

### `PATCH /api/tags/:id`

Renames or recolours a tag: send `name`, `color`, or both. Only what's sent changes; `"color": null` removes the colour. Every recipe with the tag shows the change.

**Responses:** 200 with the [Tag](#tag); 400 as for POST; 404 `{ "error": "Tag not found." }`; 409 `{ "error": "That name already exists." }`.

### `DELETE /api/tags/:id`

Deletes the tag and takes it off every recipe that has it. Unlike an ingredient, a recipe depends on nothing in a tag, so there's no 409.

**Responses:** 200 `{ "message": "Tag deleted successfully." }`; 404 `{ "error": "Tag not found." }`.

## Equipment

A shared list, managed exactly like [ingredients](#ingredients) (3b), at `/api/equipment`: `GET` (list, with `search`, `limit` and `offset`), `GET /:id`, `POST` and `PATCH` with `{ "name": "…" }` (trimmed and lowercased, then 1–100 characters), and `DELETE`.

**Responses:** as for ingredients, with these messages: 404 `{ "error": "Equipment not found." }`; 409 `{ "error": "That name already exists." }`; 409 `{ "error": "Cannot delete equipment that is used in recipes." }`.

## Images

A recipe's photos (3b). Every upload is untrusted, so it's checked and re-encoded, and only the re-encoded files are kept (D11).

### `POST /api/recipes/:id/images`

Adds one image to a recipe. Send `multipart/form-data` with the file in a field called `image`, and nothing else:

```bash
curl -F image=@photo.jpg http://localhost:3000/api/recipes/09b75162-d37f-476c-b87a-30bbba971058/images
```

1. **Type:** JPEG, PNG or WebP, recognised from the file's first bytes, not its name or `Content-Type`. Anything else, including SVG, GIF and HEIC, is a 415. (A phone's camera, or its browser when sending a photo, gives JPEG.)
2. **Size:** at most 15 MB (413).
3. **Pixels:** at most 50 megapixels, read from the image's header before it's decoded, so a small file that would expand into an enormous image is refused (400).
4. **Re-encoding:** the image is turned upright from its orientation tag, then saved as WebP at most 2,000 px on its longest side (never enlarged), with a thumbnail at most 400 px. Re-encoding drops all metadata, including the GPS position phones record.
5. **Limit:** 10 images per recipe (409).
6. **The main image:** a recipe's first image becomes its main one (`primaryImageId`).

The recipe's `updatedAt`, and so its [ETag](#etags-and-if-match), moves.

**Responses:**
- 201 with the [Image](#image)
- 400 `{ "error": "Send one image, in a form field called \"image\"." }` for no file, another field, or more than one file; `"That file isn't a readable image."`; `"Images can be at most 50 megapixels."`
- 404 `{ "error": "Recipe not found." }`
- 409 `{ "error": "A recipe can have at most 10 images." }`
- 413 `{ "error": "Images can be at most 15 MB." }`
- 415 `{ "error": "Only JPEG, PNG and WebP images are accepted." }`

### `DELETE /api/images/:id`

Deletes an image and its files. The recipe's `updatedAt` moves. If it was the main image, the next one in upload order becomes the main one, or, if it was the last, the one before it; deleting the only image leaves none.

**Responses:** 200 `{ "message": "Image deleted successfully." }`; 404 `{ "error": "Image not found." }`.

### The files: `/media/<id>.webp` and `/media/<id>-thumb.webp`

Each image is two WebP files, named after its id: the image, and its thumbnail. They're served outside `/api`, with `Content-Type: image/webp` and `Cache-Control: public, max-age=31536000, immutable`, since a file never changes: a new upload gets a new id. Any other name under `/media` is a 404.

The API keeps them in `MEDIA_DIR` (by default `media/` in the working directory; on the Pi, the `media` volume). They aren't in the snapshot: an app caches them itself.

## Sync

### `GET /api/sync`

Everything a device needs to work offline, in one response (Phase 3c). The web client keeps it as its offline copy.

```json
{
  "recipes": [ … ],
  "ingredients": [ … ],
  "etags": { "0b9e6a52-…": "\"1763836800123\"", … },
  "tags": [ … ],
  "equipment": [ … ]
}
```

- `recipes`: every [Recipe](#recipe), exactly as `GET /api/recipes/:id` returns it, lines and images included, sorted by name, then id. The image files themselves aren't in it.
- `ingredients`: every [Ingredient](#ingredient), sorted by name, then id.
- `etags`: each recipe's id, with the [ETag](#etags-and-if-match) its own `GET` sends. A device that edits a recipe from its copy sends that ETag in `If-Match`, so a change made elsewhere meanwhile gets a 412 rather than being overwritten. They're opaque here too.

- `tags` and `equipment` (3b): every [Tag](#tag) (without `recipeCount`) and every [Equipment](#equipment) item, sorted by name, then id.

A deleted recipe is simply missing from the next snapshot. Renaming or recolouring a tag changes the snapshot too, so its ETag changes.

The same data always gives the same bytes, and the `ETag` is a hash of them. Send the ETag of the copy you have in `If-None-Match`:

```http
GET /api/sync
If-None-Match: "pY2m0rB7wq1cZ0vT4lX9eNnKjH3sD8aF6uQ5iE2oL1g"
```

| `If-None-Match` | Response |
|---|---|
| Not sent | 200 with the snapshot |
| The current ETag, its weak form (`W/"…"`), a list containing it, or `*` | 304 with no body: your copy is current |
| Anything else | 200 with the snapshot and its new ETag |

The response carries `Cache-Control: no-cache`, so a browser's cache always checks with the API before reusing a stored copy. Treat the ETag as opaque.

**Responses:** 200 with the snapshot and its `ETag`; 304 when unchanged.

## Units

A line's `unit` must be one of these symbols or aliases. Matching ignores case, spaces around the unit, repeated spaces and one trailing full stop, so `" Tbsp. "` becomes `tbsp`. Responses always use the symbol. Leave the unit out, or send null or `""`, for a count such as "3 eggs".

| Symbol | Aliases | Measures |
|---|---|---|
| `g` | gram, grams, gr | mass |
| `kg` | kilogram, kilograms, kgs | mass |
| `oz` | ounce, ounces | mass |
| `lb` | pound, pounds, lbs | mass |
| `ml` | millilitre, millilitres, milliliter, milliliters, mls | volume |
| `l` | litre, litres, liter, liters | volume |
| `tsp` | teaspoon, teaspoons, tsps | volume |
| `tbsp` | tablespoon, tablespoons, tbs, tbsps | volume |
| `cup` | cups | volume |
| `fl oz` | fluid ounce, fluid ounces, floz | volume |
| `pinch` | pinches | other |
| `clove` | cloves | other |
| `slice` | slices | other |
| `can` | cans, tin, tins | other |
| `bunch` | bunches | other |
| `handful` | handfuls | other |

An unknown unit is a 400 whose message lists the symbols. The list lives in `shared/units.ts`, which the web client uses too; adding a unit is a code change, not a migration.

## Errors

Every error body has an `error` message. Validation errors add `fields`, with one message per field:

```json
{
  "error": "Validation failed.",
  "fields": {
    "servings": "Must be a whole number.",
    "ingredients.0.unit": "Unknown unit \"handfull\". Use one of: g, kg, oz, lb, ml, l, tsp, tbsp, cup, fl oz, pinch, clove, slice, can, bunch, handful, or none for a count.",
    "ingredients.1.quantityMax": "Only allowed when quantity is set.",
    "createdAt": "Unknown field."
  }
}
```

Nested fields use dotted paths: `ingredients.0.unit` is the first line's unit. A problem with the body as a whole, such as a missing body, is reported under `(input)`.

| Status | Meaning |
|---|---|
| 400 | Validation failed, the body isn't valid JSON (`"The request body is not valid JSON."`), a recipe names an ingredient, tag, equipment item or main image that isn't there, or an image upload isn't readable or is over 50 megapixels |
| 404 | The recipe, ingredient, tag, equipment item or image in the URL doesn't exist, or the path under `/api` is unknown (`{ "error": "Not found." }`). Outside `/api` and `/media`, a GET for a page gets the web client's `index.html` instead, so its own routes work as links; a missing file, or any other request, gets Express's plain HTML 404 |
| 409 | An ingredient, tag or equipment name is already taken, an ingredient or item is still used by a recipe, a new recipe's `id` is taken, or a recipe has 10 images already |
| 412 | `If-Match` doesn't match the recipe's current ETag (`"The recipe has changed since it was loaded."`) |
| 413 | The body is over 100 kB (`"request entity too large"`), or an image over 15 MB |
| 415 | An image that isn't JPEG, PNG or WebP |
| 500 | Something unexpected. The body is always `{ "error": "Internal server error" }`; details go only to the server log |
| 503 | Health check only: the database can't be reached |
